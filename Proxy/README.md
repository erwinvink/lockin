# OpenAI coach proxy

This proxy keeps the OpenAI API key out of the iOS app.

```bash
npm install
cp .env.example .env
npm run dev
```

Put the real `OPENAI_API_KEY` in `.env`. Keep `.env` local or on your server only; commit `.env.example`, not `.env`. `GARMIN_SERVICE_URL` points at the internal Garmin sidecar (`GarminService/`), defaulting to `http://127.0.0.1:8788`.

Environment:

| Var | Default | Meaning |
| --- | --- | --- |
| `OPENAI_API_KEY` | — | OpenAI key for the coach. |
| `OPENAI_TIMEOUT_MS` | `300000` | Budget for one Responses API call; a call past it is aborted and answered as HTTP 504. The scheduler treats an automatic plan still `generating` after 30 minutes as interrupted, which assumes this stays at about 5 minutes or less. |
| `COACH_CHAT_TIMEOUT_MS` | `45000` | Budget for the coach-chat model call. Past it the chat answers with the built-in quick answer instead. Keep it under the app's 60-second chat timeout. |
| `COACH_CHAT_REASONING_EFFORT` | `low` | Reasoning effort for coach-chat calls on reasoning models (`gpt-5*`, `gpt-6*`, `o*`). `off` leaves the parameter out. |
| `PORT` | `8787` | Listen port. |
| `LOCKIN_APP_TOKEN` | unset | Shared app credential. When set, every route except `GET /health` requires the header `X-Lockin-App-Token: <value>` (constant-time compare) and answers `401 {"error": ...}` otherwise. When unset the proxy stays open and logs a warning at startup. Set it in production and give the same value to the app. |
| `COACH_ALLOWED_MODELS` | `gpt-6.1-sol,gpt-5.5,gpt-5-mini` | Comma-separated models the coach may use. A request for any other model (or none) silently uses the default model, `gpt-6.1-sol`. `GET /models` only lists allowed models. There is no `OPENAI_MODEL` override; the default lives in `src/model-selection.ts`. |
| `LOCKIN_AUTH_SECRET` | dev secret | HMAC secret for `/v1` storage bearer tokens. Tokens expire 180 days after they were issued. With `NODE_ENV=production` and no secret, every `/v1` route answers `503` instead of signing with the built-in development secret. |
| `NODE_ENV` | — | `production` turns on the `/v1` secret check above. |
| `GARMIN_SERVICE_URL` | `http://127.0.0.1:8788` | Internal Garmin sidecar. |
| `GARMIN_SYNC_STATE_PATH` | `.data/garmin-sync-state.json` | Durable watch-sync state. |
| `AUTO_PLAN_STATE_PATH` | `.data/auto-plan-state.json` | Automatic planning state. A file that is not valid JSON is moved to `<path>.corrupt-<timestamp>` and planning starts from an empty state. |
| `AUTO_PLANNER_DISABLED` / `AUTO_PLANNER_INTERVAL_MS` | — / `900000` | Turn off, or change the tick of, the planning scheduler (nightly runs, retries after failures, recovery of runs interrupted by a restart). |
| `LOCKIN_DB_PATH` | `.data/lockin.sqlite` | `/v1` storage database. |
| `OPENAI_TELEMETRY_PATH`, `OPENAI_TELEMETRY_STDOUT`, `OPENAI_TELEMETRY_DISABLED` | see below | Telemetry. |

OpenAI coach telemetry is enabled by default. Each Responses API call writes a start and finish event to `.data/openai-usage.jsonl` and logs a compact `openai.telemetry ...` line to stdout. The finish event includes route, phase, model, latency, input/output/reasoning tokens, cached input tokens, cache hit rate, and an estimated USD cost when the model is in the local price table. Override the file path with `OPENAI_TELEMETRY_PATH`, set `OPENAI_TELEMETRY_STDOUT=0` to keep only the JSONL file, or set `OPENAI_TELEMETRY_DISABLED=1` to disable it.

The app plans through `POST /plan/trigger` (its coach request plus the trigger; the proxy decides whether to plan, plans, stores the plan per user, and the nightly scheduler re-plans from the last request the app sent) and reads the stored plan with `GET /plan/status?userId=...`. When the athlete has a race goal the plan is a combined week: the proxy plans the running week first with `src/coach/skills/running-coach-planner`, validates it, then plans the strength week around the accepted runs with `src/coach/skills/fitness-coach-planner` and cross-checks the combined week. `POST /generate-week` runs the same combined pipeline directly and answers with the week; the app no longer calls it. Both planners get the computed training signals and the guardrails the validators enforce (`src/coach/planner/running-guardrails.ts`, `strength-guardrails.ts` with `strength-limits.ts`, `session-budget.ts`, `overreaching.ts`, `assessment.ts` and the shared `goal-metrics.ts`): weekly km, long-run and climbing caps, running floors, hard-run rules, plausible targets, strength working caps, set bounds and progression bands. Safety flags never waive a limit. Safe fixes (shortening easy runs to the weekly cap, dropping or replacing an implausible target, lowering an over-cap or unearned rep target) are applied before validation and listed in the response's `adjustments`; anything else gets one repair attempt (`src/coach/plan-pipeline.ts`), then a 422. The coach context for `/plan/trigger` and the nightly plans, `/generate-week`, `/coach-verdict` and `/coach-chat` is enriched with the last four days of Garmin wellness when the sidecar is reachable and the request carries a `userId` (cached per user for 10 minutes; a context sent without Garmin data is logged with the reason). Metrics the sidecar lists in `unavailableMetrics`, and 0/empty values, are passed to the coach as `null` (no data), never as real low values.

Periodization and continuity (`src/coach/planner/season.ts`, `periodization.ts`, `running-phase-limits.ts`, `strength-phase.ts`, `current-plan.ts`):

- Season (`coachContext.season`), computed from the stored race and the week start: race state (upcoming; recent, inside the post-race window; none), phase (general preparation with no race ahead or more than 16 weeks out, base, build, peak, taper in the final 21 days, transition after the race) and emphasis, with a plain reason. The post-race window is one day per 4 race km, 7-28 days (14 after 54 km, 25 after 100 km); a past race never reads as in taper or "0 weeks out".

- Planned recovery weeks (3:1) on the plan-block calendar: after three loading weeks in a row, counted from `planBlockStartedAt` or the last unloading week (a reactive offload, a low-volume week, the taper or the race; for a hybrid athlete a reactive offload is pain 4+ or very weak feedback only, so strength effort ratings or a deloaded strength session never reset the running count), the next block week is a recovery week (`coachContext.periodization`). Running drops to at most 75% of the four block weeks before with one quality session and a shorter long run; strength cuts hard sets to 60% of the last loading week, one hard session, at most 3 sets per goal exercise, no progression, and no tests except a due test on the week's last 2 days. The rule is stateless, so every nightly re-plan inside the week agrees; "The recovery week is over." follows a planned recovery week only (not the post-race weeks or a low-volume week).
- Taper and race window, per day of the rolling week: 80% of the pre-taper volume 15-21 days out, at most 70% 8-14 days out, race-week shakeouts only (50% of a normal easy run, max 8 km), no hill load inside 10 days; after the race easy or recovery runs only the first week, then easy runs, recovery runs and an easy long run (no tempo, intervals or hills) until the post-race window ends; strength light in the last 10 days and nothing hard within 4; after the race strength is capped per day (nothing hard on post-race days 1-2, no very_hard or max_output and so no tests on days 3-7, normal from day 8) while upper-body progression and the session minimum carry on.
- Running floors (`guardrails.floors`) in general preparation, base, build and peak, for weeks of 3 or more runs, counted over 7 days: today's run (locked; done, else planned) plus the planned runs. At least one tempo, interval or hill run (the long run does not count; a quality run or a race today counts, a race being the quality stimulus of its week, and after a hard run today, a tune-up race included, the next day is no hard run) and at least the smaller of 85% of the four-week training average and last week's training km (races left out), so the floor never asks for more than holding last week. In the first 3 weeks after the post-race transition the four-week average still carries the taper and the race, so the floor reads the average training week of the four weeks before the taper instead (when higher; computed from the whole run history the app sends, `running.preTaperTrainingWeekKm`, since the context keeps only the last 30 runs): it then holds last week rather than letting the week shrink. The floor never asks for every run at its cap: at most 90% of what today's run and the week's runs hold at the long-run cap (`frequency.maxRuns` runs at `longRun.capKm`), rounded down to the half kilometre. The weekly km cap counts the same 7 days (the clamp shortens easy runs to what today's run leaves; the floor yields if it would exceed the cap). When the current plan cannot reach a floor (each kept run grown by at most 15% and within its own cap, plus the running days it leaves free, offset 6 included), or would stay above this week's weekly or long-run cap even 15% shorter, that is a continuity change signal. The cap's reference (the 7 days and the 4 weeks before today) ends at local midnight, like the floor's. Lifted in the taper and the post-race transition, by a computed relaxation (a wellness gate is not one, and the profile note never is), for a starter base or the first week back after 4+ weeks without runs, when no day away from the long run, the day after a hard run today and a wellness gate's 48 hours is free (quality) and when the race window reaches into the week or the free days cannot hold it under the long-run cap (km). `trainingSignals.running.noSpeedStimulusLast3Weeks` flags an easy share of 0.95 or more over 3 weeks (races left out) in those phases.
- Lifted floors name their reason in plain words (`RELAXATION_LABELS`, such as "a planned recovery week"), and the repair messages list every computed reason from the same labels. The hard-run cap (2 in 3-4 runs, 3 in 5 or more) counts the same 7 days: today's run is one of the runs from 3 km (a short jog is not), and then a hard one when it is long, tempo, intervals, hills or a race. The recovery-week and taper long-run ratios read the longest training run of the last 6 weeks, races left out, and both easy shares leave races out.
- Long run and climbing: no run (the race day excepted) above 1.15x the longest training run of the last 30 days, races and runs on the race date left out (the race is reported as demonstrated capacity; with no training run in 30 days, the longest of 42 days; with none, the 20 km return-week cap; with no runs on record, the app's recent longest run); weekly climbing over the same 7 days, today's run included, at most the larger of 1.25x the average week of the 4 weeks before today (races left out) and 300 m (no cap without run history); over it the climbing comes off the easy and recovery runs first, then the long run, and the hill and quality runs last. The Garmin HRV gate reads the latest day with an HRV reading while it is at most 2 days old, and the sleep gate the last 3 nights that have a score, so the 01:30 plan, before today's row has data, still sees them. Likewise the coach read's Garmin values (HRV, sleep score, training readiness, resting HR) and the low-readiness flag each read the latest day that has the value, at most 2 days old, and the signals carry that day (`hrvDate`, `sleepScoreDate`, ...), so yesterday's number is never presented as today's.
- The profile note is planner context only (`coachContext.profile.profileNotes`): it shapes exercise and run choice within the limits and relaxes no rule, so no running floor, run count or strength minimum. Free text cannot be read precisely enough to relax a week safely. Logged pain lowers the plan instead: a logged session with pain 4 or more puts readiness in `recovery_needed`, which lifts the running floors and the strength minimum. Readiness `overreaching` comes from strength logs only and eases only the strength week: it relaxes no running floor and does not replace the planned 3:1 recovery week. This holds until the app has a structured pain or injury field.
- Wellness gate (`wellness-gate.ts`): HRV below the athlete's baseline (Garmin LOW or POOR, or a 7-day average below the baseline range when the sidecar sends `hrvWeeklyAvgMs` and `hrvBaselineLowMs`; UNBALANCED alone is no gate) or a sleep score below 50 on 2 of the last 3 nights. It lifts no floor: tempo, interval and hill runs in the next 48 hours become easy runs, and the week's quality run must fall on a later day away from the long run (the quality floor is lifted only when no such day is left). It is a continuity change signal.
- Plan continuity: the planned future sessions (`coachContext.currentPlan`) go to both planners with the computed change signals since the plan was made (including a new season phase, such as general preparation the day after the post-race window, and "Readiness is back to normal" when the plan was made while readiness was overreaching or recovery needed: that state is recomputed from the logs up to the plan time). With no signal, a re-planned run keeps its kind and stays within 15% of its distance; other changes are listed in `adjustments`.
- Readiness is time-based (pain >= 4 or very weak feedback counts for 7 days and a later clean log clears it); plateaus come from rolling 3-week windows; after a new plan block the current level is the baseline plus the block's own logs.
- The exercise library carries pull-up, push-up and plank ladders with selection rules by current max; names are exact (schema enum, validator and the app's `ExerciseKind` are kept identical by a test) and equipment is checked.

Delivered work against the plan (`src/coach/planner/delivered-work.ts`): the coach judges a session by what the athlete actually did, not only by what was planned. Each logged goal result is compared with its own session's planned target (any effort label, tests excluded); "more than planned" starts at 2 reps (5 s on a plank) and 10% above it.

- More than planned explains a higher effort rating: those sessions never count toward `recent_effort_above_plan` or `repeated_high_perceived_effort`, they count as clean, and they earn progression even on light or technique work. Only effort above plan on work done as planned, falling short, pain and very weak feedback are warning signs.
- Lower logged numbers that meet a lighter planned week (taper, recovery week, after a race) are not a decline (`rollingTrend.lowerNumbersFollowLighterPlan`); a decline needs results below the plan.
- Progression plans from the level shown: after more than planned, `allowedTopTarget` runs from the useful floor (45% of the current best, or the earned step if higher) to the working cap; a previous prescription below the useful floor restarts at that floor, and hold and recovery-week bands never cap below it.
- Volume: a normal week (normal readiness, no recovery week, not the taper) plans at least 3 strength sessions whatever the running week (running load, hard runs and the weeks after a race never hold upper-body progression or lower the minimum), never more than the free training days allow around one full rest day (`minSessionsThisWeek`), and goal work uses 3-6 sets (2-3 in a recovery week or the taper, 2-6 otherwise; `goalSetsPerExercise` states the week's range); 2-set work is raised in the clamp. A recovery week, the taper or a recovery need (logged pain of 4 or more) has no session minimum; the profile note never lowers it.
- The rule reaches every model prompt from the one constant (`DELIVERED_WORK_PRINCIPLE` in `coach-temperament.ts`): both planners as `outputRules.deliveredWork`, the coach read and the coach chat through the shared coach voice; the skills spell it out. The chat never prescribes extra sessions, but work done beyond the plan on a good day counts and the coach plans from it. New-log change signals say "did more than planned", and the chat sees `deliveredVsPlan` per log.

Strength readiness, tests and weekly structure (`effort-flags.ts`, `readiness-state.ts`, `overreaching.ts`, `assessment.ts`, `session-budget.ts`, `strength-limits.ts`):

- Readiness ladder, judged against the plan (tests, work planned very_hard and rated as planned, and sessions with clearly more than planned never count as excess effort): calibrate when 2 of the last 5 sessions done as planned were rated 2 or more RPE above plan; only the goal exercises those sessions trained hold (no progression, no extra set) and readiness stays normal. Overreaching needs that flag plus a second marker within 14 days (a shortfall on a target completed cleanly before, the flag persisting in 3 of the last 5, or 2 of the last 5 rated Weak or Very weak), or a decline with at least 2 results below plan; for the next 3-7 days each goal exercise's top block holds or steps back one step, one set fewer per block, 30-50% fewer hard sets, no tests. Pain of 4 or more or very weak feedback is `recovery_needed`.
- Due tests: a goal exercise is due for a test 42 days after its last test or the plan block's baseline, 28 days when its progression is blocked at the cap and the set limit or session budget, or on a plateau, in a normal-readiness week. Tests pause in the taper phase, judged per day (a week that starts before the taper takes no test on its days inside it), on post-race days 1-7, and in a recovery week except its last 2 days. A due test is one max set on a listed fresh day, enforced.
- The useful floor is 45% of the current best, rounded up, from a best of 2 reps (the plank from 10 s). In a normal week the top working target never sits below it and every progression band starts at it or above (missed sessions may lower the target down to it, never below); each goal exercise (pull-ups with a pull-up bar) appears in at least 2 sessions as useful work at the floor or more, or a test (3 x 9 push-ups for a best of 40 is no exposure). A session whose goal work of an exercise is all below the floor at medium effort or harder has its top block raised to the floor when another session reaches it (a lighter finisher behind a block at the floor stays; a week whose top block is below the floor is sent back).
- Session budget: a goal exercise's useful sets x reps (seconds for the plank) in one session stay at or below 3.0x the best for pull-ups and 3.5x for push-ups and the plank; a second block gives way first, and the set route stops at the budget (a metric blocked there is due for a test sooner).

Coach requests may carry an optional `timeZone` (IANA id, e.g. `Europe/Amsterdam`). `weekStart` is the athlete's local midnight today; with `timeZone` "today" ends at the next local midnight (correct on 23- and 25-hour DST days), without it 24 hours later. Adherence only counts sessions scheduled before today; today's not-yet-done sessions are reported as `pendingToday` and stay out of the score. Running days: `running.runningDays` empty means unconstrained (any future day 1-6); selected days with no offset left this week mean zero runs.

`POST /coach-chat` takes `{request, messages}`: the same coach request the plan routes take, plus up to the last 20 chat turns (`{role: "user" | "coach", text, createdAt?}`). It builds the same coach context, training signals and coach read as `/coach-verdict`, then asks the athlete's chosen model (`request.model`, resolved like the other routes) for a structured answer: `answer` (60-180 words), `evidence`, 2-3 `followUpPrompts` and `answerKind`. The prompt lives in `src/coach/chat-prompt.ts`; the call, the output checks and the fallback live in `src/coach/chat-model.ts`. Without an API key, or when the call fails, times out or returns unusable output, the route answers with the built-in template answer from `src/coach/chat.ts` and `usedModel: false` (the reason is logged as `coach_chat.fallback`). The chat never changes the plan. Request bodies over 2 MB get `413`; invalid JSON or a malformed chat payload gets `400`; other failures get a generic `500` with the details in the server log.

The legacy strength-only route `POST https://lockin.elevenfactor.com/generate-week-plan` still accepts local training data and the selected model ID. The proxy loads `src/coach/skills/fitness-coach-planner`, builds a deterministic coaching context, calls OpenAI with the skill instructions and references, and runs technical validation on the structured JSON before the app accepts it. This route intentionally skips Garmin enrichment.

Garmin beta routes (all proxied to the sidecar, never exposing it publicly). Every Garmin route requires `userId` to be the app's profile UUID (any case) and answers `400` otherwise, so a request can never fall through to the sidecar's default (owner) Garmin account or name another token directory:

- `POST /garmin/connect` — body `{userId,email,password,mfaCode?}`; creates a per-user Garmin token session. Passwords are used for this login call only and are not stored by Lockin.
- `POST /garmin/disconnect` — body `{userId}`; removes that user's token session.
- `GET /garmin/status?userId=...` — sidecar reachability plus Garmin connection state (`{ok,userId,loggedIn,state,connectedEmail,lastError}`).
- `GET /garmin/snapshot?userId=...&sinceDays=N` — status, wellness days, and running activities in one response (default 7). A wellness day may carry `unavailableMetrics: [...]` naming fields whose Garmin call failed; their `0`/`""` values are placeholders and must not be stored.
- `POST /garmin/sync-plan` — body `{userId,planRevisionId,staleWorkoutIds,workouts,lockedThroughDate?}`; durable desired-state sync for future planned runs. `lockedThroughDate` (`yyyy-MM-dd`, the athlete's local today) protects recorded workouts: today's stays on the watch when left out of `workouts`, and runs dated before it are dropped from the sync state (no longer listed, counted or pushed) while their Garmin workouts stay as history. Only explicit `staleWorkoutIds` delete a workout from Garmin. Without it the proxy uses today in `Europe/Amsterdam`.
- `GET /garmin/sync-status?userId=...` — current watch-plan sync state.
- `POST /garmin/retry-sync` — body `{userId}`; retries failed or blocked watch sync operations.
- Legacy passthrough remains available: `POST /garmin/push-workouts` and `POST /garmin/delete-workouts` (no app callers), now also requiring `userId`.

Push/delete contract: the app-facing response shape is `{results: [...], error?}` and is canonical — the sidecar returns bare result arrays today, and `src/garmin/garmin-client.ts` normalizes both shapes so neither side breaks the other. Durable plan sync state is stored in `.data/garmin-sync-state.json` by default; override with `GARMIN_SYNC_STATE_PATH`.

Check `GET https://lockin.elevenfactor.com/health` to confirm the proxy is running and has an API key (the only route that never needs the app token). The app's AI Coach context tab stores the selected model ID and can refresh available text model IDs through `GET https://lockin.elevenfactor.com/models`, which lists only allowed models.

The request includes baseline numbers, target goals, sessions per week, equipment, target date, recent SwiftData logs, and planned/completed sessions. Each log marks whether pull-ups, push-ups, and plank were actually tested so the model does not treat an unlogged exercise as a zero.
