Seven phases, one recovery budget.

The sequence protects the app from becoming messy: first stabilize the current strength loop, then add reflection, running, and multi-coach orchestration.

PHASE 01

Stabilize Strength

Make the existing pull-up, push-up, and plank coach trustworthy before the app gets wider.

  • Explain AI week planning
  • Tighten completed, missed, partial, and deload logs
  • Keep the current proxy boundary
PHASE 02

Server Architecture Spike

Decide whether coach skills, schemas, validation, and context building should move to your server.

  • Compare local proxy, server, and hybrid
  • Define privacy rules
  • Keep iOS as clean as possible
PHASE 03

Journal and Sentiment

Make reflection useful without turning Lockin into a full diary app first.

  • Daily mood, energy, fatigue, soreness, stress
  • Short journal entries
  • Coach-visible summaries
PHASE 04

Running Foundation

Add endurance training carefully before jumping into full ultra complexity.

  • Running goals and run logs
  • Easy, long, recovery, hill, and tempo sessions
  • Weekly load across strength and running
PHASE 05

Ultra-Running Mode

Support real long-range preparation: terrain, fueling, race profile, taper, and recovery blocks.

  • Race distance, date, elevation, cutoff
  • Back-to-back long runs
  • Injury and overtraining warnings
PHASE 06

Multi-Coach Orchestration

Let specialists propose plans, then have one synthesis coach resolve conflicts.

  • Strength coach proposal
  • Ultra coach proposal
  • Synthesis coach final plan
PHASE 07

Habit System Polish

Turn Today into a daily command center that makes the next right action obvious.

  • Today training, check-in, journal shortcut
  • Weekly review
  • Progress across strength, running, consistency, recovery

Specialists first. Synthesis last.

The clean model is not one huge prompt. Each coach owns a bounded domain, and the synthesis coach is responsible for tradeoffs.

Strength Coach

Strict reps, real progression.

Owns pull-ups, push-ups, plank, strict form, deloads, missed workouts, and benchmark pressure.

  • Pull-up and push-up progression
  • Plank and trunk strength
  • Strength maintenance during high mileage weeks
Ultra Coach

Miles without wreckage.

Owns base mileage, long runs, terrain, recovery, fueling practice, race goals, and injury risk.

  • Easy runs, long runs, hills, tempo
  • Fueling and gear rehearsals
  • Taper and recovery weeks
Synthesis Coach

The one plan you follow.

Reads both specialists plus journals, sentiment, pain, fatigue, and adherence to return one integrated week.

  • Conflict resolution
  • Recovery budget management
  • Short explanations for plan changes

The server decision is a product decision.

Moving skills to a server is not just infrastructure. It decides privacy, coach versioning, app complexity, sync, and how much context coaches can safely use.

Local proxy only

Simple for development, private by default, but awkward once coaches need schedule, sync, and shared history.

Hybrid

Keep local mode for development. Add server mode for real use, versioned skills, orchestration, and validation.

Server now

Cleanest long-term architecture, but it forces account, sync, and privacy choices earlier.

Recommended default

Hybrid. The current proxy remains useful, while the long-term coach system gets a cleaner home.

Open decisions.

These are the choices that should stay explicit before implementation makes them accidentally permanent.

  • Is Lockin personal-only, or should it become multi-user from the start?
  • Should journals sync to a server, stay local, or sync only as summaries?
  • Should the synthesis coach be allowed to read raw journal entries?
  • Should running plans optimize for distance, time-on-feet, or race date first?
  • Should strength goals remain equal priority once ultra training begins?
  • Should Apple Health import be part of the first running version, or later?
  • Should manual running logs come before GPS and watch data?
